¿Por qué escalar WebSockets es más difícil que escalar REST?

Long image

A

Answer

Porque cada conexión vive en un servidor concreto: con varios servidores, un evento que entra por uno debe llegar al servidor donde está conectado el destinatario.

  1. Una conexión WebSocket guarda estado en memoria de un servidor: no se puede mandar «a cualquiera» como una petición REST.1
  2. Las sticky sessions mantienen a un cliente en el mismo servidor, pero no le avisan a otro servidor que llegó un mensaje para él.2
  3. Hace falta una capa que enrute entre servidores: pub/sub, un registro de conexiones o un log.2
  4. ws-hub separa los «poolers» que guardan conexiones de los servicios con la lógica y los une con Redis.3

¿Cómo se ve una arquitectura que escala?

Diagram structure

  • Traefik (balanceador) traefik
  • Pooler WS 1 pool1
  • Pooler WS 2 pool2

  • Servicios de negocio logica
  • clientes → traefik · wss://
  • traefik → pool1
  • traefik → pool2
  • pool1 → redis · publica
  • pool2 → redis · se suscribe
  • logica → redis · eventos
  1. Traefik (balanceador) ↗

    Reparte las conexiones nuevas entre los poolers.

  2. Pooler WS 1 ↗

    Solo guarda conexiones, autentica con JWT y reenvía mensajes; no tiene lógica de negocio.

  3. Redis pub/sub + presencia ↗

    Lleva cada mensaje al pooler donde está el destinatario y guarda quién está conectado.

  4. Servicios de negocio ↗

    Deciden qué mandar y a quién; nunca hablan directo con los clientes.
